# Bixing 的论文与组会工作流

新稿给材料和一句方向。续改给项目名和改动即可。Agent 负责找上次的源文件、选图、排版、重建和验收。你可以随时指定页、图、比较条件或发布范围。

## 一句话开工

| 场景 | 可以直接这样说 | Agent 交付 |
| --- | --- | --- |
| 新 Paper | 「用这个定稿做成和 HuPER 同款的 Paper，首页放方法图。」 | 按稿本生成全文、目录、图表和引用，预览首页卡片与阅读页。 |
| 更新 Paper | 「用这份公开修订稿更新 HuPER，保留已有章节链接。」 | 核对版本差异，更新变动的正文、图和引文，沿用原地址。 |
| 新一场组会 | 「用这个目录做下周组会，八分钟，想让学长看到这次比较了什么。」 | 建立本场私有源目录，按听众和时长从原稿选证据，交付可演示 HTML。 |
| 续讲同一场 | 「接着上次 Ocula，把这个目录里的新对照加到结果后面，方法页锁定。」 | 只扩充指定部分，保留已锁源页和旧页的笔记对应关系。 |
| 改一页 | 「只改结果页，换成这个表，保留单位和对照组。先给预览。」 | 找到对应源页，核对数字，重建整份报告供直接试讲。 |

## 你决定什么

- **「这次」**作用于当前稿件或场次。可以指定听众、重点、证据、时长和结束位置。其余细节由 Agent 从原稿和上版推定。
- **「锁定」**可以指页名、图或结论。Agent 保留这些内容，按你后续的明确指令解锁或修改。插页后用页名和原笔记编号识别同一页。
- **「以后都」**才写入对应的共用规则。新场次继承约定好的模板、语言与排版。本场的删节、点评和结束页继续留在本场记录。
- **「先给提纲」或「只预览」**决定这次交付的深度。普通修改直接做成可看的本地版本。你也可以一开始就明确「验收后发布」，Agent 按这份授权完成发布和线上核验。

## Agent 怎样接着上次做

1. **定位材料。** Paper 找原网址与对应稿本，组会找上一版私有源目录。优先采用作者指定的版本、原图和表格。几个稿本有实质冲突、材料缺失会影响结论、或公开范围无法判断时，集中问一个具体问题，先做其余可核实的部分。
2. **编辑和核对。** Paper 保留全文、作者次序、引文和已使用的锚点。组会沿用 Paramecium 的白底英文模板，用原图、表格或短片承载结论。按本场方向选证据，核对图号、单位、预算和对照条件。定向修订只动对应源页。
3. **留下接续入口。** Agent 在组会私有目录维护一份简短的 `brief.md`，记录稿源、本场目的、已锁内容和已定取舍。`meeting.json` 保存标题、有序源片段和输出位置，有本场样式或脚本时再记录。下次直接复用它们。你只需用自然语言反馈。
4. **预览或发布。** 交付物附上预览和简短改动说明。Paper 核验首页、目录、图表与引用。组会核验投屏、手机、翻页和 Notes。公开 Paper 使用已确认可公开的稿本。组会私有源和口令留在网站仓库外，发布时只更新项目清单与密文。修订同一场沿用原私链。新场次替换项目固定入口会使旧私链失效，需要两场并存时可给新场次独立私链。

Paper 的 Hugo 目录和命令见[论文制作说明](papers.md)。组会的构建、稳定笔记编号和加密发布见[组会制作说明](slides.md)。原生 HTML 版式见[HuPER 组会示例](meeting/huper-example.html)。
